# 战斗 PDF 报告优化

## 版式

- 结果、回合数、双方头像、属性与积分变化直接放在第一页顶部，不再独占封面页；保留起始与最终生命/能量快照，避免精简时丢失起始数据。
- 每个回合用表格保留行动方向、伤害/闪避、进攻/防守能耗、双方生命/能量和技能。跨页重复表头，不再逐回合重复头像与多层卡片。
- 过长或多行技能在整行备注中展开，保留全文；长名称自动换行。没有回合或缺少状态时仍可生成，缺失数值明确显示 `-`。
- 状态按回合号关联至下一份快照，以表示回合结束状态；不再按两个列表的位置强行配对。记录的零能耗保持为零，不再将防守方零消耗替换成 2。胜者未记录时不默认宣布另一方获胜。

## 生成与体积

- 每名角色只请求一次报告专用画像，最长边 256 px。OSS 请求使用 JPEG 和绝对质量上限 80，不改变聊天等页面已有原图/缩略图接口。参数语义见 [OSS 图片质量文档](https://www.alibabacloud.com/help/en/oss/user-guide/adjust-image-quality)。
- 本地旧图片同样降采样并转为 JPEG；透明区域铺白。远端读取上限 2 MiB，旧图片上限 12 MiB、4,000 万像素，失败时使用小型占位图；所有流和图像读写器都会释放。
- PDF 只有两份画像资源，页脚与正文共用同一份字体。纯 ASCII 英文报告使用 PDF 标准 Helvetica；出现中文姓名、技能或生成者信息时切换至嵌入的 CJK 子集字体。
- 字体程序按固定路径复用缓存，但每份 PDF 创建独立 `PdfFont`，避免并发文档互相引用对象。启用 PDF 对象流压缩和可增量刷新的表格，采用默认压缩级别以平衡时间与体积。
- 先写临时文件，再以已知长度的输入流上传；避免整份 PDF 的内存缓冲和 `toByteArray()` 拷贝。成功和异常路径均清理文件，部署需允许 JVM 临时目录写入。
- 生成者只读取基础用户实体，省去 Token、角色及操作记录关联查询；读取放到渲染和上传之后，避免在整个生成期间持有不需要的用户头像数据。
- 先保存报告文件 ID，再标记生成完成，避免完成状态先于文件 ID 可见。

## 同一组合成样本的前后对比

优化前基线为 `master` 的 `8ab3843`。使用固定角色、合成画像和回合数据，Java 17，本机离线测试。数据库、图片获取和上传均模拟，不是生产端到端性能承诺。

| 样本 | 旧页数 | 新页数 | 旧大小（字节） | 新大小（字节） |
| --- | ---: | ---: | ---: | ---: |
| 中文，12 回合 | 5 | 1 | 1,840,872 | 约 241,000 |
| 英文，12 回合 | 5 | 1 | 1,777,340 | 约 12,350 |
| 中文，120 回合 | 34 | 5 | 6,168,204 | 约 258,000 |

120 回合样本在同一 JVM 内交替调用新旧实现，每版预热 2 次后测量 5 次；两轮对比的中位数分别为 **78 → 35 ms、75 → 33 ms**（约减少 55%）。新旧实现共用同一批数据与模拟服务，并交替先后次序。短报告的首次中文字体初始化仍有一次性成本；真实耗时还取决于数据库、OSS、画像内容、字体字符和服务负载。正常画像路径的远端请求从 4 次变为 2 次，上传数据也更小。不同轮次的时间戳与字体子集标识可能使文件大小略有变化。

同进程基准可在 Java 17 环境复现，旧类只编译到测试目录，绝不进入生产构建：

```sh
mkdir -p tmp/pdfs/baseline-src
git show 8ab3843:src/main/java/com/yichi/onepiece/data_export/service/DataExportService.java > tmp/pdfs/baseline-src/DataExportService.java
./gradlew -I scripts/pdf-baseline.gradle compilePdfBaseline -PpdfBaselineSource=tmp/pdfs/baseline-src
ONEPIECE_PDF_BASELINE_CLASSES="$PWD/build/pdf-baseline-classes" ./gradlew test --tests '*BattleReportGenerationTests' --rerun-tasks
```

仅 120 回合样本启用成对计时，输出 `PDF_PAIRED_MEDIAN`。默认测试不加载旧类，也不对耗时设易波动的断言。

## 验证与预览

- `compileJava` 和 `build -x test` 通过，75 个相关回归用例全部通过，未运行会访问外部数据库或实际发送邮件的整套集成测试。
- 验证中英文、完整/缺失/乱序状态、真实零值、空历史、无胜者、超长技能/名称、并发字体隔离、画像降采样、透明背景、超限/损坏图片、失败流关闭、上传长度和临时文件清理。
- 使用真实 OSS SDK 请求对象验证报告处理参数，并确认普通缩略图与原图参数不变；没有使用 OSS 凭证或发起实际上传。
- 已渲染检查中英文第一页、120 回合末页及长文本分页，没有重叠、截断或空白多余封面页。
- 设置 `ONEPIECE_PDF_PREVIEW_DIR=output/pdf` 并运行 `BattleReportGenerationTests` 可生成模拟报告；测试输出 `PDF_METRICS`。样本与渲染中间文件不应作为生产资源提交。

没有对外接口、DTO、MyBatis XML 或数据库迁移变更。旧的 OSS 报告文件不会自动替换；重新生成才使用新版格式。此说明随修复提交，PR 与合并状态以 GitHub 记录为准。
