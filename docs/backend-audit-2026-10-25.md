# 后端性能、内存与 BUG 检查

基线：`2af428c`（本地同步的 `origin/master`）。本轮为静态代码检查与定向回归验证，没有在线压测，也没有执行生产数据库迁移。

## 已修复

1. **高：用户资料自动转换会带出登录 Token。**
   `userDao.xml` 的用户列表使用详情映射，逐用户查询 Token；`UserConverter.toUser(UserDetailImpl)` 又将 Token 值复制到返回对象。用户列表接口仅要求 USER/LIST 权限，该权限默认分配给普通用户。相同转换器也用于问题详情中的创建者资料。
   修复：用户资料转换默认不复制 Token；列表使用不查询 Token 的独立映射，详情仍保留原查询。登录和当前账号更新流程显式设置 Token 的代码保留。
   **有意的响应变化：** 普通用户资料中的 `tokens` 不再自动填入 Token 值；字段仍保留。避免其他用户获得可用于认证的凭证。

2. **高：权限检查缺少实际抛出异常。**
   `IamService.checkPermissionOfCurrentAccount` 在当前登录角色不属于已分配角色时，只创建异常，随后继续按该角色检查权限。修复为立即拒绝。

3. **中：分享资源重复插入已有授权。**
   `UserService.shareResource` 原本将接收者全部既有资源和本次请求拼接后一起插入。每次分享都会复制旧授权，请求内部重复 ID 也会增加数据。
   修复：已有授权转为集合，仅批量插入去重后的新增 ID，空批次不调用 DAO。覆盖连续重复请求；并发请求仍需数据库唯一约束保证，见后文。

4. **中：OSS 下载流没有关闭。**
   文件下载和 PDF 图片读取都直接 `readAllBytes()`，没有关闭返回的 OSS 流。这会占用连接池资源；重复下载、生成报告或读取失败时可能耗尽连接。
   修复：两处使用 try-with-resources，正常和异常路径都会关闭输入流。文件响应与图片回退逻辑保留。

5. **性能：战斗计分为得到场次数而加载全部历史。**
   `BattleService.getKFactorOfCharacter` 原本调用 `listBattlesByCharacterId(...).size()`，需要完整结果对象，并触发战斗视图的嵌套查询。
   修复：新增数据库 `COUNT(*)` 查询，仅返回整数，保留原列表查询的 LEFT JOIN 和参与者条件，避免改变原统计口径。原列表接口继续用于展示。

## 仍需处理的发现

以下为代码证据，不代表已经通过在线环境复现；本轮未修改这些流程。

- **高：资源分享缺少资源级授权检查。** `UserService.shareResource` 没有验证发送者是否拥有或有权分享请求中的资源。控制器仅检查 USER/UPDATE，随后可以直接新增 `user_resource`。需要按资源类型检查创建者、共享权限与系统资源规则。
- **高：好友申请接受流程没有校验申请方向和待处理状态。** `acceptFriend` 使用双向查询找到双方的任意关系后全部改为 ACCEPTED。申请发起者也可能调用接口接受自己发出的申请。应限制为当前用户是接收者、状态为 APPLIED 的记录，并原子更新。
- **中：验证码消费不是原子的。** 验证码先查询、后标记使用，并发请求可能同时通过检查。应使用带 `is_used = false` 和过期条件的更新，以影响行数决定验证是否成功，并与业务写入组合事务。
- **中：分享授权缺少数据库唯一约束。** 本轮过滤重复 ID 不能阻止两个并发请求同时插入。应先清理历史重复数据，再为 `(user_id, resource_type, resource_id)` 增加唯一约束，并处理重复键。
- **中：组织层级允许形成环。** `GroupService.addGroup` 未防止把自身或祖先设为子组织；`GroupDao.listAllFatherGroups` 使用不带环检测的递归查询。可能导致详情查询达到数据库递归上限而失败。
- **性能：多域视图仍有嵌套查询。** battle、character、fruit、group、user、issue 的 XML 使用 `association select`。如战斗列表每行最多加载执行记录、两名角色、两份操作记录；实际 SQL 数量受 MyBatis 本地缓存影响。宜逐域拆分列表与详情，使用 JOIN 或批量查询并在真实 MySQL 上验证映射。
- **性能/内存：上一条、下一条查询返回整个 ID 列表。** 多个 DAO 的查询排序后未加 LIMIT，服务只取第一个。可改为数据库 `LIMIT 1`，并确定排序键相同的稳定顺序。
- **性能/内存：组织成员操作重复构建列表。** `GroupService.addCharacter` 在过滤每个角色时重新执行 `groupMatchEntities.stream().map(...).toList()`。预先构建 ID 集合可将重复扫描变为集合查找。
- **内存：图片与文件下载仍完整读入再 Base64 编码。** `readAllBytes()` 和编码结果会同时占用内存，Base64 本身还会增加数据体积。更大的优化需要新增二进制/流式下载接口，或受控的 OSS 签名 URL，并设置大小与并发限制；本轮保留现有 Base64 API。

## 验证范围

- Java 17 下 `compileJava` 通过，保留原有 MapStruct 与弃用 API 警告。
- 15 个定向回归用例通过：权限拒绝、Token 不外泄、MyBatis 列表/详情映射分离、连续重复分享、两种流的异常关闭、计分边界、H2 下统计 SQL。
- 测试不依赖 OSS 凭证，不发送邮件，不连接生产数据库。
- MyBatis XML 已用项目 UUID 类型处理器解析验证；真实 MySQL 的用户列表、登录、问题详情仍应做一次烟测。
- `build -x test` 打包通过。未执行整个集成测试套件：现有套件包含数据库连接及实际邮件发送，定向回归测试单独执行。
